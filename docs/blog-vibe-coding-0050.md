# 從一句話到自動更新的股市儀表板：Vibe Coding 如何改寫企業的軟體開發流程

「寫一個互動式網頁，可以分析 0050 成交量變化。」

這是一句再普通不過的中文需求，沒有規格書、沒有線框圖、沒有技術名詞。但在三個工作階段之後，它變成了一個部署在 GitHub Pages 上、每個交易日收盤後自動更新的台股分析儀表板：即時價量圖表、三大法人買賣超追蹤、規則型買點訊號、跨市場投資比較，甚至還有一份用十年還原股價實算的「誰打敗 0050」排行榜。

整個過程中，人類沒有寫過一行程式碼。這不是概念驗證，而是一個真實運作中的產品。本文完整拆解這個案例，並回答企業最關心的問題：當 AI 能把一句話變成產品，組織裡的「開發」與「人才」該如何重新定義？

## 一、Vibe Coding：不是「AI 全自動」，而是新的人機分工

Vibe Coding（氛圍編程）指的是開發者用自然語言描述意圖，由 AI 代理（如 Claude Code）負責實作、除錯與部署的工作模式。許多人誤解它是「AI 全自動寫程式」，但真實案例告訴我們：它更像一種嚴謹的分工——

**人負責三件事：提出需求、驗收成果、發現不對勁。AI 負責三件事：實作、解釋、修正。**

在這個案例中，人類總共只下了六個關鍵指令，每一個都是「目的」而非「實作」：

1. 「寫一個互動式網頁，可以分析 0050 成交量變化」
2. 「價格不正確，不是最新的，請直接建立 GitHub Pages」
3. 「我要能點選區間與圖表，就可以即時更新」
4. 「增加三大法人＋散戶持股變化，與可購買時間點建議」
5. 「增加自選台股與美股比較，包含外匯、利率，結合經濟學理論」
6. 「請上網分析過去十年哪一檔股票打敗 0050」

注意第二句：使用者沒有說「請檢查資料串接邏輯」，只說了一個觀察到的事實——「價格不正確」。AI 自己診斷出原因（開發環境連不到證交所、頁面退回了示範資料），並提出解法：把資料抓取搬到 GitHub Actions 的雲端排程上，每天自動向證交所取得真實行情。**用事實回報問題，讓 AI 找原因**，是 Vibe Coding 最重要的溝通技巧。

再看第五句與第六句，需求的複雜度已經跨越了一般認知中「AI 助手」的能力邊界。第五句要求跨市場比較：系統要能讓使用者輸入任意台股代號、下拉選擇美股標的，把 0050、台積電、SPY 換算成同一基準的指數化報酬曲線，附上年化波動、相關係數與 Beta 統計，再疊上美元兌台幣匯率與台美利率——並用利率平價、折現估值模型、現代投資組合理論等經濟學框架，把當下區間的實際數據翻譯成投資語言。第六句則要求 AI 先上網做研究，再用十年還原股價（含股息再投入）實際計算四十四檔台灣中大型股的報酬：結果顯示 0050 十年賺 8.29 倍、年化 23.7%，樣本中僅約半數個股能夠打敗它。每一項功能，都是在一句中文之後的數分鐘內上線。

## 二、真正的價值藏在「踩坑」裡

如果只看成果，這個案例像一場魔術表演。但對企業真正有價值的，是過程中五次真實的「事故與排除」——因為這正是導入 AI 開發時，組織必然會遇到的場景。

**第一坑：權限。** 首次推送程式碼到 GitHub 被 403 拒絕，原因是 GitHub App 未被授予該儲存庫的寫入權限。AI 無法替你按下授權按鈕——資安邊界仍然掌握在人手上，這是設計，不是缺陷。

**第二坑：部署權限的繞道。** 用官方 API 建立 GitHub Pages 站台再度被拒（workflow 的預設權杖沒有管理權限）。AI 的解法展現了資深工程師的判斷力：改用 gh-pages 分支部署法，由使用者本人的憑證推出第一版以觸發自動啟用，之後交給機器人維護。

**第三坑：資料源反爬。** 短時間內兩次全量抓取 26 個月資料，證交所開始對雲端 IP 回應 HTTP 307 限流。解法是改為「增量更新」——已有快照時只補抓最近兩個月，並且「抓取失敗不擋部署」，網站永遠沿用最近一次成功的資料。對公開 API 保持禮貌，是資料工程的基本素養。

**第四坑：來源替換。** 原本選用的 Stooq 與 FRED 對 CI 執行器直接封鎖。AI 當場改用 Yahoo Finance 與紐約聯儲的公開 API，全數成功。教訓：資料管線必須假設「任何來源都可能失效」，替代方案是架構的一部分。

**第五坑：最危險的一種錯。** Yahoo 的美債殖利率代號 ^TNX 回傳值已是百分比，程式又除以十，畫出了「0.46%」的十年期美債殖利率——語法全對、圖表漂亮、數字錯了十倍。發現它的不是編譯器，而是常識。**AI 時代最常見的錯誤不是程式跑不動，而是「看起來很對的錯數字」**，這正是人類驗收力無可取代的原因。

## 三、對企業的三個啟示

**啟示一：需求表達力成為核心技能。** 案例中最有效的指令都遵循同一個模式——講目的、不講實作、一次一個需求、做完就驗收。這與敏捷開發的用戶故事（User Story）精神一致，差別在於回饋週期從「兩週一個迭代」壓縮到「幾分鐘一次對話」。這意味著人才盤點的標準正在改變：懂領域知識的業務人員，只要掌握需求表達與驗收的方法，就能直接產出過去需要一個小型開發團隊才能完成的工具。能把業務意圖說清楚的人，就是新的開發者。

**啟示二：驗收力與資料素養是新的品管防線。** 當實作成本趨近於零，品質的瓶頸移到了驗收端。企業需要的不再只是會寫程式的人，而是能對 AI 產出提問的人：這個數字的來源是什麼？計算方式合理嗎？跟外部基準對得起來嗎？案例中的十年報酬排行榜特別在頁面上標註了「存活者偏差」警語——十年前沒有人能預知世芯會漲 184 倍，而當時的股王大立光只剩 1.45 倍。這種方法論上的誠實，必須由人來把關。

**啟示三：自動化管線讓「作品」變成「產品」。** 一次性的網頁只是作品；接上 GitHub Actions 之後——每個交易日 15:30 自動抓資料、提交版本化的資料快照、重新部署——它才成為無人值守的產品。整條管線沒有伺服器、沒有資料庫、零維運成本，全部建立在免費的公開基礎設施上。對預算有限的團隊，這是極具參考價值的架構範式。

值得一提的是，這條管線的設計本身就內建了韌性：任何一個資料來源暫時失效，都不會讓網站停擺，系統會沿用最近一次成功的快照繼續服務，隔日排程自動補齊。「失敗不擋部署」這條原則，適用於所有依賴外部資料的企業應用。

這個專案從第一句需求到十年報酬分析上線，累計的人類輸入不到三百字；但它能成立，靠的是那三百字背後的判斷：知道要什麼、看得出哪裡不對、堅持每個數字都要對得起來源。

AI 沒有取代開發，它把開發還原成了決策。
